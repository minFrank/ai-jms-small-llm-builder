# 本地 AI 系列 · 发布验收标准(闸门)

## 为什么要有这份东西

第 02 期审了 **8 轮**,每轮都还有问题。用户问了两个问题,答案如下:

**① 为什么再跑一轮还有这么多处?**

因为原来的流程**缺三样东西**:

| 缺什么 | 后果 |
|---|---|
| **验收判据** | 没有"什么样算通过",所以只能一轮轮改 |
| **审查人的"通过权"** | 六个 agent 每次只输出"建议",它们**天然只会提问题** —— 让一个模型挑毛病,它永远挑得出 |
| **轮次上限** | 我按"阻断归零"判断,而阻断永远归不了零 |

再叠加一个事实:**我每轮都在改稿,而改动本身会引入新问题**(实测约占 22%)。
于是变成:改 → 引入新问题 → 再审 → 再改 …… 没有终点。

**② 业界标准是多少?**

查了三个领域的真实做法:

- **出版业(三审三校)** —— 维基百科「校对」条:审稿在排版前进行,校对在排版后进行;
  **"所有修正内容,不论大小,均再次送交校对人员检查并签署"**。
  → 关键是**"签署"**:校对签署 = 明确宣布通过。三审三校是**固定轮次**,不是无限循环。
- **软件工程(code review)** —— 审阅人可以说 **LGTM**(looks good to me),即有权宣布"可以合入"。
- **Google SRE(error budget)** —— 原话:
  > "we strive to make a service reliable enough, but **no more reliable than it needs to be**"
  > "an incremental improvement in reliability may cost 100x more than the previous increment"
  → **可靠性不是越高越好**:过了某个点,每提高一点的成本是上一次的 100 倍,而用户感知不到。
  → 换成审核:**追求"零问题"是错误的**,目标是"足够好"。

**三个领域的共同点**:固定轮次 + 明确判据 + **有人能宣布通过**。
我原来三样都缺。

## 验收标准(发布闸门)

### A. 硬性项(全部通过才能发)

| # | 项目 | 判据 | 谁来判 |
|---|---|---|---|
| A1 | **数据有日志** | 每个数字都能在 `logs/` 指到具体行(或如实标注"无日志") | 一审 + 机械自检 |
| A2 | **四张数据齐** | 速度 / 资源 / 效果(含失败案例)/ 门槛,缺一张不发 | 审查 Agent |
| A3 | **绝不推收费模型** | 全文无付费、注册、免费额度、试用钩子 | 三审 |
| A4 | **许可核实** | 写了许可结论,且有官方来源(仓库 LICENSE / 模型页 license 字段) | 三审 |
| A5 | **门槛一句话能答** | 读者能立刻回答"我的电脑能不能跑"(用表格或一句话结论) | 三审 + 通读 |
| A6 | **前 5 段零术语** | 无量化/GGUF/token/权重/模型/运行环境等 | 二审 + 机械自检 |
| A7 | **无黑话与夸大词** | 无"一键出片/秒出/神器/颠覆"等 | 机械自检 |
| A8 | **数字三处一致** | digest ↔ 正文 ↔ 图内数字一致 | 一审 + 机械自检 |
| A9 | **机械自检全绿** | `selfcheck_article.py` 退出码 0 | 脚本 |
| A10 | **合规** | 隐私边界、克隆他人的法律风险、AI 声明齐备 | 三审 |
| A11 | **失败案例真实** | 至少一个失败案例,报错与日志逐字一致 | 一审 |
| A12 | **重复度达标** | ① 同一概念（内存门槛 / 磁盘体积 / 速度 / 中文文件名坑 / 坑一 / 许可 / 微信语音）**摊在 ≥3 个小节即不合格**；② 单概念出现次数不超上限（8G ≤3、体积口径 ≤3、独立显卡 ≤2、中文文件名 ≤2、许可/商用 ≤4）；③ 开头段之间相似度 < 0.45 | 机械自检（`⑤b 同一概念跨节重复` + `④c 重复强调`）+ 人工抽读 |
| A13 | **排版达标** | `scripts/check_wechat_layout.py` 全绿（A 微信兼容 / B 排版要素 / C 阅读节奏 三组共 21 项）；发布前还必须跑 `preview_wechat_style.py` 用手机宽度（414px）目视确认 | 脚本 + 人工目视 |

### B. 建议项(可以带着发,不阻断)

| # | 项目 | 处理 |
|---|---|---|
| B1 | 措辞可更顺 | 记录,下一期改进 |

### C. 轮次规则

- **最多 3 轮**:首轮全量审 → 定向复验 → 定向复验
- 到第 3 轮时,**A 类全过即定稿**,无论 B 类还剩多少条
- 若第 3 轮 A 类仍有不过项,只修行内问题,不再重跑全流程

## 为什么会有 A12（2026-09-14 补）

第 02 期走完 8 轮三审三校后，**用户打回**：「文章是不是有重复机械的片段？」

量出来确认属实：**内存 8G 出现在 5 个小节、中文文件名坑 3 个小节、坑一 3 个小节各讲一遍**；
「不是 X，是 Y」这个句式用了 **9 次**；「许可/商用」出现 **14 次**；开头两段相似度 0.50（同一句话说了两遍）。

**为什么 8 轮都没抓出来 —— 三个结构性缺口:**

| 缺口 | 说明 |
|---|---|
| **① 检查粒度不对** | 机械自检只查「句子级重复」（≥25 字的句子相同）。而跨节重复的是**同一件事、句子写法完全不同**（「它平时只吃 6.0–6.5G」vs「6.5G 不是小数」）→ 字面不同，抓不到 |
| **② 没有角色负责「信息效率」** | 一审查事实（重复的事实不违规）· 二审查读不读得懂（**重复反而更易懂**）· 三审查合规 · 校对查机械错误（重复不算错）。**四个维度里没有「啰嗦」这一维** |
| **③ 阈值本身就是防线的漏洞** | 「重复强调」这条规则原本设 8G 上限 **6 次**，起因就是曾被读者察觉重复；结果稿子长到**正好 6 次**，判定「达标」放过。**阈值设松了等于没有** |

**根因一句话**：我把「教学性重复」（换个说法再强调一次，读者受益）和「结构性重复」（每节独立成文，各把同一批事实重讲一遍，读者疲劳）**混为一谈**，按前者设了宽松阈值。

**所以 A12 不是加一条检查，是补一个审查维度。** 它进 A 类（硬性项）—— 定稿前必须过。

## 为什么会有 A13（2026-09-14 补）

用户看到推送到草稿箱的稿子后反馈：**「整个内容排版美观程度很差劲，在微信公众号后台基本很丑。」**

诊断出「丑」的具体来源（都不是审美问题，是**缺件**）：

| # | 缺失 | 后果 |
|---|---|---|
| 1 | **没有 padding** | 文字直接贴边（微信编辑器默认 0 边距） |
| 2 | **没有字号/行距基准** | 依赖微信默认 17px，长文读起来挤 |
| 3 | **没有字距** | 中文挤在一起 |
| 4 | **列表标记没转换** | markdown 的 `- ` 原样输出 → 微信里显示成「- 第一项」，一堆带横杠的段落 |
| 5 | **图片没样式** | 无圆角、无间距，直接贴在文字上 |
| 6 | **表格没斑马纹** | 密不透气 |
| 7 | **没用 `<section>` 容器** | 字体基准无法统一继承 |
| 8 | **标题只有加粗** | h2 在长文里是主力分隔，只有加粗＝没有视觉层级 |

**所以 A13 不是"审美检查"，是"缺件检查"** —— 判据全是可机械判定的：
微信兼容（A 组）· 排版要素齐全（B 组）· 阅读节奏（C 组）。

查证依据：微信图文的 HTML/CSS 白名单（支持 font-size/margin/padding/line-height/
letter-spacing/border-radius/box-shadow/mark；**不支持** `<style>` 块、媒体查询、
`position`、`id` —— 写了会被剥掉，等于白做）。样式表落在
`content-admin/app/services/wechat_theme.py`，支持 light / warm / mono 三主题。

**这一条必须排在推送之前**：排版是"发出去就改不了"的东西（微信已发表仅能改 120 字）。
