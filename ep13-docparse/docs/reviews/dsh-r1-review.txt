一、P0 致命问题（跑测会失败或数据不可用）

C-01 【P0｜C】
位置：§3 主循环，第 88–91 行。
问题：超阈扩展至 12 的逻辑没有实现。`if n >= 8: break` 在 IQR 仍大于 10% 时直接结束；后面的 `if n >= 12: break` 永远不可达（n>=8 已先 break）。设计稿自己的注释写着「超阈固定加跑至 12 封顶」，代码却是到 8 即停，注释与实现互相矛盾。
依据：V6c §2.2 F-01/X-01：`IQR/median>10% → extension_target=12（扩展期内 max_attempts=12）`；`cell.done := (n_valid≥6 且 IQR 合格) 或 n_attempt ≥ max_attempts(8 或 12) 或 fatal`。
修法：改成显式两阶段状态机：初期限 8；第 6–8 个有效 rep 仍超阈时把 max_attempts 置为 12 并继续；到 12 仍超阈置 `unstable=true` 后 done。删除 12 的死分支，增加单测覆盖「6 次达标」「8 次仍超阈→12」「12 次仍超阈」。

C-02 【P0】
位置：§3 主循环，第 83–91 行。
问题：用 `n = len(valid_reps)` 的有效 rep 数代替尝试数。`max_attempts` 约束的是 attempt，失败、超时、skipped 也占 attempt；全失败时 n 永远为 0，`while True` 没有任何出口。另 `reps.push(cell)` 把 cell 当 rep 压入，`valid_reps` 未定义，伪代码不可直接实现。
依据：V6c §2.2 分列 `n_attempt` 与 `n_valid`，并明确「max_attempts 是硬终止，任何阶段到点即停」；§3.5「retry 有界（1 次+退避）」。
修法：每轮先 `attempt += 1`；失败/超时也写 rep；只有 ok 才 `n_valid += 1`；每轮入口先判 `n_attempt >= max_attempts`；所有失败路径必须能终止；伪代码区分 cell 与 rep 对象。

C-03 【P0｜C】
位置：§3 主循环；§4 status 枚举。
问题：没有实现 `n_valid<4 → status=failed`、`4≤n_valid<6 → status=partial`、`12 次有效后仍>10% → unstable:true 只报分布不排名`、`median≤0 → 报错`。status 用 `done` 代替 `complete`，partial 只是枚举值没有判定规则，失败格和部分格无法按规格进入分母/单列。
依据：V6c §2.2 明文规定上述四种收尾；§3.2 status 四态为 `complete/partial/failed/skipped`。
修法：把四条规则写进 `cell.done` 状态机；status 严格用四态；partial 进分母但不进名次、单列数量与清单；unstable 引擎只报分布；median≤0 直接标错并留痕。

C-04 【P0｜C】
位置：§3 第 92 行；§4 第 118 行。
问题：两处都写「jsonschema 校验在 save 之前」，与规格 F-05 的 save_raw 先行相反。校验一旦失败，cell 根本不会落盘，正好复现 F-05 要修的丢格。第 92 行又说「校验失败也留失败记录」，逻辑上自相矛盾：失败记录同样要过同一 schema。
依据：V6c §3.5：`finally: cell.save_raw(); try validate_schema(cell); except SchemaErr as e: cell.schema_err=str(e); cell.save_raw()`；F-05「先落盘，永不因校验丢失」。
修法：先 save_raw（至少含 status/err_kind/原始 reps）→ validate_soft → 失败写 schema_err 再 save_raw。raw 与 validated 分层，禁止把 validate 作为落盘前置条件。

C-05 【P0｜C】
位置：§3 第 84 行；同节停止语义表。
问题：控制检查放在 `while True` 的 rep 循环内，会在 cell 中途暂停/停止，违反同一节「格间安全停（当前格跑完才停）」和 F-13。cell 可能停在半成品状态，status 无法定义，且与「paused 是 run 级状态、不产生 cell 状态」冲突。
依据：V6c §3.5/§3.8 F-13：rep 循环内不查控制；只在 sample 边界、cell 落盘后 `control_desired()`；§4.1 pause 在 sample 边界 ack。
修法：删除 rep 循环内的控制检查；移到 `finally save+validate` 之后、下一 sample 之前；ack 后再进入 pause/stop；补「停止发生在格中」的测试，确认当前格完整落盘。

C-06 【P0｜C】
位置：§3 第 85 行；§1 runner 心跳描述。
问题：心跳写在 sample 边界（cell 落盘后），而单格实测可长达 16.5 分钟。V6c 的 stale 判据是连续 15s 无 heartbeat，按此设计会被误判为 run 死亡，可能被 supervisor 杀掉；也没有独立心跳进程。
依据：V6c §4.1 F-14；§3.8 `start_heartbeat(control/, interval=5, process="independent")`。
修法：独立进程每 5s 写 task.json（tmp+rename 原子写），与推理完全解耦；格边界只更新 last_progress/ack；stale 判定同时检查 owner_pid 是否存活，活着标 stalled 而非直接判死。

C-07 【P0｜C】
位置：§4 第 104–105 行；§1 cells 路径。
问题：主键写成 `cell_id`，值含 run_id 和 `/`（`ep13-20261104-143000-oxr/book_01`）；路径 `cells/<run_id>/<engine>/<sample>.json` 比规格多一层 engine。run_id 本身又带 `-oxr`，等于每引擎一个 run，与「一个 run 跑全引擎、sessions/<run_id>.json 一份」的 run 级聚合冲突。
依据：V6c §3.2 F-03：`cell_key=<sample_id>__<engine>__p<page>`，不含 run_id；路径 `cells/<run_id>/<cell_key>.json`（run 只一层）；API `GET /api/cells?run_id=&cell_key=` 走 query 避免 `/`；§3.8 一个 run 内循环 engines。
修法：改用 `cell_key`；sample_id 用 UUID；路径只保留一层 run 目录；run_id 不按引擎拆分；删除 cell_id 中的 `/`；API 用 query 参数。

C-08 【P0｜C】
位置：§4 第 103–115 行。
问题：这不是 v6 cell schema。required 缺 `schema, cell_key, layer, set, input, target_valid, max_attempts, n_attempt, n_valid, n_fail, wall_median, wall_iqr, fingerprint, err`；status 的 `done` 不在 enum；rep 用 `rep/wall_s/ok/text/fail_reason`，缺 `n/attempt/status/wall/wall_self/cer/err_kind/ts`；没有 `cell_success_rate/trunc_rate/unstable/engine_session_id/peak_rss_mb/rss_scope`；`timing.cold_load_s` 放在格内。按设计稿字段生成的 cell 无法通过 §3.2 的 v6 schema；若改用 v6 schema，写入代码又缺字段——两者必有一边失败。
依据：V6c §3.2 required/enum/nullable 与示例；F-04；F-12。
修法：以 `schema/cell.schema.json` 为唯一实现源，逐字段照 §3.2 重写；status 四态；rep.status 四态 `ok/fail/timeout/skipped`；补聚合字段；cold_load 移到 `sessions/engines/<run_id>/<engine>.json`；写入与聚合两侧都 validate。

C-09 【P0｜C】
位置：§4 第 110–113 行。
问题：溯源信息不足且错位。`version` 只有 git/spec/weights_sha/deps，缺 `config_hash, extract_v, gt_v, sample_sha, engine_version, host_manifest_id, seed, order`；`gt_hash` 放顶层，规格要求进 `fingerprint`；没有 `input{kind,sha256,page_no,dpi}`、没有 `layer`、没有 `set`，`sample` 也不是 UUID。G0 的分组一致性矩阵、GT 逐格比对、按层排名都无法执行。

C-10 【P0｜C】
位置：§5 G0 行。
问题：G0 判据被改成「预期格数=实有格数；每格 rep 数达标；版本指纹全格一致；控制文件 mtime 在本期内」。其中「版本指纹全格一致」若按字面执行必然失败：weights_sha 逐引擎不同、gt_hash/sample_sha 逐样本不同、deps 逐 venv 不同。G0 还缺四态分母、failed/expected≤2%、skipped 按 err_kind 单列、SOURCES 无「待补」、GT 逐格 `gt_v+gt_hash` 比对、caliber audit passed 且 `finished_at>run.started_at`。「控制文件 mtime」不是审计时效。
依据：V6c §4.5 G0（F-06/F-07/F-08/F-17）；四态 pass/fail/not_run/stale。

C-11 【P0｜C】
位置：§1/§3/§5；§2.1。
问题：6 引擎分母没有重算。规格 S26 expected=208、S24=192（8 引擎），95% 最小样本量写的是「≥192 cells 的 95% 即 ≥183 valid」；该口径本身把「engine 级」和「总样本 192」混在一起，修订时需明确是总量还是逐引擎。按总量口径折算，6 引擎 S26=156、S24=144，最小样本量约 S26≥149、S24≥137；若按逐引擎 95% 口径，则 S26=26 需≥25、S24=24 需≥23。S_PDF 应为页数×6。设计稿只写「26 样本×6 引擎」，没有 sets.yaml、没有 S24/S26/S_PDF/S_ALL 的区别，也没说主榜用哪个。若沿用 208/192，G0 必然失败或阈值失效。
依据：V6c §2.1（sets.yaml 唯一分母；N-04/F-06）；§2.2 95% 阈值与最小样本量；§1 P-1=A。

六、判定与开工前必改清单
======================================================================

判定：需大改（不是需小改，不可开工）。

理由：问题不是文字措辞，而是三处数据根基与唯一权威源不一致：
1) 协议 A 的终止/扩展/失败分级不成立，会出现「超阈不扩展」「全失败死循环」「partial/failed 无定义」；

3) G0–G3 被整体重排，6 引擎分母/95% 阈值未重算，按现稿跑会出现「6 引擎数据用 8 引擎门槛发布」或「G0 直接失败」。

1. 协议 A 状态机：attempt/valid 分离；8→12 两阶段；partial/failed/unstable/median≤0；控制只在格边界；独立 5s 心跳。配单测。
2. cell schema：直接落 `schema/cell.schema.json`，逐字段照 V6c §3.2；cell_key/路径/status 四态/rep 四态/input/layer/set/fingerprint/聚合字段；save_raw 先于 validate。

4. 6 引擎分母：sets.yaml 冻结 S26=156、S24=144、S_PDF=页数×6；95% 最小样本量重算（S26≥149、S24≥137）；reps 上限 1872/1728；主榜 S24 与 S26 关系写死。
5. 运行架构：runner 单进程 + 每引擎 venv worker + NDJSON IPC/分块/单飞/每命令 timeout；WorkerFatal respawn 预算；teardown RSS/端口断言；control task.json 状态机/lease/ack/restart/reset。
