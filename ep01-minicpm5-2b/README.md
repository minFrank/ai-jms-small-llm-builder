# ep01 · 无显卡跑 2.5B 小模型(MiniCPM5-2B 实测)

第 01 期:**没有独立显卡**的电脑,把 2.5B 参数的小模型跑起来,并测出真实数据。

配套文章:「AI 创意｜9月11日:无显卡跑 2.5B 模型」(公众号 AI 积木师)。
本目录是那篇文章的**复刻包** —— 文章里的每个数字都能在 `logs/` 里指到具体一行。

> 第 01 期发布时本仓库尚未建立,代码原先放在 `ai-radar-trend` 仓库;现按仓库规范归位到本目录。

## 门槛(先看这个,不够就别折腾)

| 项 | 要求 |
|---|---|
| **下载体积** | **0.5–3 GB 档**:Q4_K_M 1.45 GiB(Q8_0 2.49 GiB + llama.cpp 运行时约 20 MB) |
| **要不要显卡** | **不要**,纯 CPU 跑(本文实测机器无独显) |
| 内存 | 8 GB 起(**必须限上下文**,见下) |
| 磁盘 | 4 GB |
| 系统 | Windows 10/11 x64(llama.cpp 有 CPU 免编译包) |
| 花费 | **0 元**,模型与运行时都是开源免费 |

## 三步跑起来

```bash
# 1) 下载 llama.cpp 的 Windows CPU 版(约 18MB,免编译)
#    https://github.com/ggml-org/llama.cpp/releases
#    找 llama-bXXXXX-bin-win-cpu-x64.zip,解压到 D:\tools\llama

# 2) 下载模型(Q4_K_M 这一档,1.56GB)
#    https://huggingface.co/openbmb/MiniCPM5-2B-GGUF  ->  MiniCPM5-2B-Q4_K_M.gguf
#    放到 D:\models\MiniCPM5-2B-Q4_K_M.gguf

# 3) 跑一句话
D:\tools\llama\llama-completion.exe ^
  -m D:\models\MiniCPM5-2B-Q4_K_M.gguf ^
  -c 4096 -t 8 -n 200 ^
  -p "用一句话解释什么是模型量化。"
```

> **关键提醒**:必须加 `-c 4096`(或更小)。不加的话模型会按自带的 128K 上下文加载,
> 内存直接吃到 **7.7 GB**;限到 4096 后只要 **2.5 GB**。这是这一期最容易踩的坑。

## 四张实测数据

实测机器:AMD Ryzen 7 5700G(8 核 16 线程)· 27.9 GB 内存 · **无独立显卡** · Windows 11

### ① 速度

| 量化档 | 文件大小 | 提示处理 | 生成速度 |
|---|---|---|---|
| **Q4_K_M** | 1.45 GiB | **143.8 t/s** | **18.02 t/s** |
| Q8_0 | 2.49 GiB | 68.2 t/s | 11.67 t/s |

其他维度:

| 场景 | 结果 |
|---|---|
| 线程曲线 | 4 → 15.4 / **8 → 16.2** / 16 → 15.8 t/s(**8 线程最优**) |
| 并发吞吐 | 单路 16.4 → 4 路 **33.6 t/s**(8 路另批次约 52 t/s) |
| 长上下文 | 8 千字"大海捞针"命中;读题约 107 t/s(约 25 秒) |

### ② 资源占用

| 项 | 结果 |
|---|---|
| 进程内存峰值 | **2488 MB**(Q4_K_M)/ 2512 MB(Q8_0) |
| CPU 峰值 | 37% |
| 上下文 → 内存 | 默认 128K:**7.7 GB**;限 4096:**2.5 GB** |

### ③ 真实任务效果(5 类质量抽样,含耗时)

| 任务 | 耗时 | 输出 tokens |
|---|---|---|
| 常识 | 25.0 s | 436 |
| 数学 | 35.2 s | 627 |
| 逻辑 | 13.4 s | 231 |
| 指令遵循 | 23.0 s | 417 |
| 中文写作 | 35.5 s | 624 |

原始文本(含模型实际输出)在 `quality/` 目录,可自行判断水平。

### ④ 门槛

见文首表格。**一句总结**:8 GB 内存 + 4 GB 磁盘 + 0 元,不用显卡,就能跑。

## 必须知道的坑(实测踩到)

1. **思维链会"吃掉"答案** —— 模型习惯先输出大段推演,默认 200 token 预算常在推演阶段就用完,
   答案被截断。→ 输出预算给到 **400 以上**,或明确要求"直接给答案"。
2. **不加 `-c` 就按 128K 上下文加载**,内存从 2.5 GB 跳到 7.7 GB —— 8 GB 机器会直接崩。
3. **线程不是越多越快** —— 8 线程最优(可复现),16 线程明显掉速。
   但跑分波动大:同一命令两次测下来整体差约 15%,**别拿单次成绩当结论**。

完整坑列表见 `README-原始版.md`。

## 数字溯源

### 溯源状态说明(重要)

第 01 期发布时,**内存、CPU、线程曲线这三项是手工记录的,原始日志没有留存**。
按仓库「数字可溯源」的规矩,2026-09-13 在同一台机器上补测并留档:

| 项 | 当年手记 | 补测结果 | 结论 |
|---|---|---|---|
| 内存峰值 | 2488 MB | **2487.8 MB** | ✅ 吻合 |
| CPU 峰值 | 37% | **36.8%** | ✅ 吻合 |
| 线程曲线 8 线程最优 | 16.2 t/s | **17.57 t/s** | ✅ 结论一致(见下) |

线程曲线测了两次,结论不变但**波动要记住**:

| 线程 | 原文 | 补测① | 补测② |
|---|---|---|---|
| 4 | 15.4 | 21.10 | 16.27 |
| **8** | **16.2** | 20.70 | **17.57** |
| 16 | 15.8 | 18.97 | 16.69 |

→ **"8 线程最优"可复现**(补测②与原文趋势一致)。
→ 但补测①显示 4 线程更高,原因是**测速波动**:同一命令、同一台机器,两次整体差约 15%
  (补测①在机器同时跑着别的任务时测得)。**单次跑分不足以支撑"最优线程数"这类结论,至少测两次。**
